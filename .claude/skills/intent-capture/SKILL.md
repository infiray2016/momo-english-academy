# intent 작성 (Plan 단계)

intent 는 "무엇을, 왜, 어떤 제약 아래 원하는가"를 요청자의 말로 적은 한 쪽짜리 파일이다. 해결책(화면 · 테이블 · 호출)은 적지 않는다 — 그것은 spec 의 몫이다.

## 절차
1. **인터뷰** — 요청자가 설명을 마치면 아래 가운데 답이 비어 있는 것만 두세 개씩 묻는다. 정본 spec 에 이미 있는 것은 묻지 말고 찾아서 채운다.
   - 지금 누가 무엇을 못 하는가? 얼마나 자주, 어떤 비용이 드는가?
   - 해결됐다고 판단할 기준은? 확인 가능한 사실로 말할 수 있는가?
   - 누가 영향을 받는가(아이 · 부모)? 어느 부분이 바뀌는가?
   - 지켜야 할 것은? 이미 확정된 결정(정본 13절 번호 · 날짜) · 비용 · 기기 · 스택
   - 이번에 하지 않는 것은?
   - 아직 정해지지 않은 것과 정할 사람은?
2. **작성** — 템플릿대로 한 쪽 이내, 절마다 두 문장에서 다섯 줄. 요청자의 표현을 살리되 모호한 말은 인터뷰 답으로 구체화한다.
3. **되읽기** — 요청자에게 보여 주고 "내 말이 맞다"고 할 때까지 고친다.
4. **저장** — `intent/YYYY-MM-DD-<슬러그>/intent.md`(변경 단위 폴더, 플레이북), 상태 `draft`. `intent/README.md` 표에 한 줄 더한다.
5. **승인** — 요청자가 `approved` 로 바꾸면 `spec-design` 으로 넘어간다.

## 템플릿
```markdown
# Intent: <무엇을 원하는지 한 줄>

작성자: <이름 (역할)> · 작성일: YYYY-MM-DD · 상태: draft | review | approved | closed
출처: <대화 · 메모 — 없으면 "대화"> · 승인: <이름, 일자 — 승인 전에는 비움>

## 문제 (Problem)
## 기대 결과 (Proposed outcome)   ← 성공 기준은 확인 가능한 사실로, 범위 밖도 여기에
## 영향받는 사용자와 시스템 (Affected users and systems)
## 제약 (Constraints)   ← 확정된 결정은 정본 13절의 날짜 · 내용으로 가리킨다
## 미결 사항 (Open questions)
```

## 쓰면서 지킬 것
- 해결책을 적지 않는다. "확인 버튼을 넣는다"가 아니라 "아이가 바로 맞았는지 알 수 있어야 한다".
- 성공 기준은 확인 가능하게. "재미있게"가 아니라 "부모 도움 없이 세션을 끝까지 한다".
- 용어는 영역 · 단계 · 단원. 절이 다섯 줄을 넘으면 요청이 둘 섞인 것 — 파일을 나눈다.
- 상태는 파일 안에 둔다. 철회는 지우지 않고 closed + 사유.
