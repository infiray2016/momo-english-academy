# plan 작성 (Build 단계)

plan 은 승인된 spec 하나를 구현하는 계획이다. **바뀌는 파일, 작업 순서, 위험, 증명** 네 가지를 적는다. 이 파일만 읽고도 다른 세션 · 서브에이전트가 구현할 수 있어야 하므로 필요한 사실(설정 키 · 상태 이름 · 문구)을 옮겨 적는다. 설계는 바꾸지 않는다 — 바뀌어야 하면 spec 으로 돌아간다.

## 절차
1. **읽기** — spec 의 설계 · 수용 기준 · 문서 반영을 읽고, 저장소에서 실제로 손댈 파일을 열어 본다(추측 금지). 정본 수정 항목은 작업 순서 맨 앞.
2. **캐묻기** — 파일마다 "무엇이 깨질 수 있는가"(같은 테이블 · 설정 키 · 공용 컴포넌트 · 순수 함수를 쓰는 곳, 마이그레이션 순서)를 묻고 위험 절에 적는다.
3. **쪼개기** — 작업을 번호 매기고 독립인 것은 병렬 표시(∥). 한 plan 은 PR 하나 분량(파일 열 개 · 단계 여덟 이하) — 넘치면 plan 을 나누고 묶음 plan 에 배정표를 둔다.
4. **증명을 먼저** — AC-n 마다 어떤 테스트 · 검사가 증명하는지 이름으로 적는다.
5. **작성** — `intent/YYYY-MM-DD-<슬러그>/plan.md`(변경 단위 폴더, spec.md 옆), 상태 draft. 작업 장부는 `.superpowers/sdd/<날짜-주제>/`(progress.md, 브리프 `task-*.md`, 보고 `task-*-report.md`, 검토 `review-*.md`).
6. **승인** — 요청자가 approved. 그 뒤 구현: 브리프 → implementer(구현 · 테스트) → code-reviewer(diff 검토) → fix 라운드 → design-reviewer(화면이면 스크린샷 대조). 동시에 다섯까지(프로젝트 CLAUDE.md, C142).
7. **갱신** — 끝나면 완료 보고 절을 채우고 done. 계획과 다르게 한 것 · 남긴 것을 숨기지 않는다.

## 템플릿
```markdown
# Plan: <spec 제목과 같게>

spec: <경로> · intent: <경로> · 작성일: YYYY-MM-DD · 상태: draft | approved | in-progress | done
승인: <이름, 일자> · 브랜치 · 워크트리: <feature/…> · 작업 장부: .superpowers/sdd/<…>/

## 목표 (Goal)                 ← spec 요약과 핵심 규칙을 3~5문장으로 옮겨 적는다. 정본 절 · 설정 키 · 문구 포함
## 바뀌는 파일 (Files that change)   ← | 파일 | 신규 / 수정 | 무엇을 |
## 작업 순서 (Order of work)   ← 번호, [문서] [DB] [서버] [화면] [검증] [사람], ∥ 병렬, 단계마다 완료 판정 한 줄
## 위험 · 제약 (Risks)         ← 깨질 수 있는 것 · 되돌리기 · 권한이 필요한 작업([사람]) · 원칙 경계
## 증명 (Proof)                ← | 수용 기준 | 증명 | 파일 · 명령 | 린트 · 빌드 · 테스트는 항상 포함
## 완료 보고 (Done)            ← 구현 뒤 갱신: 실제 바뀐 파일(계획과 다른 것 표시) · 테스트 결과 · 남긴 것 · PR
```

## 쓰면서 지킬 것
- 자족성. 다른 세션이 이 파일만으로 시작할 수 있는가.
- 설계 변경 금지. 구현 중 spec 과 다르게 해야 하면 plan 에 적고 spec 을 먼저 고친다.
- 증명은 이름으로. "충분히 테스트한다"는 증명이 아니다.
- 권한이 필요한 단계([사람] — Supabase 프로젝트 생성 · 환경 변수 · 배포)를 표시한다.
- 끝나면 갱신. 완료 보고 없는 plan 은 끝난 것이 아니다.
