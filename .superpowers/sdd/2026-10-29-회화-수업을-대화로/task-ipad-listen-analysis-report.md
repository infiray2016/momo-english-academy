## 3. 물음 1: as≈35ms + 소리 없음은 어떻게 나오는가(가설 순위)

### H1(1순위, 기록이 지지): iPad 쪽 소리 입력 경로가 '이미 열린 것처럼' 굳은 상태

- **근거**: 빠른 as + 소리 없음은 표 A 에서 24/24 실패입니다. 같은 꼴은 앱이 오디오 세션 꼴을 바꾼 관찰 쪽 실험(10-22 2732~2734 · 2832~2834 · 2943~2945)에서도 나왔고, C109 는 그 조건을 "사파리 인식이 소리를 받지 못한다"로 적었습니다(`specs/10-결정-기록.md:278`). 성공한 듣기의 as(278~1633)는 입력 경로를 새로 여는 데 드는 시간으로 보입니다. 실패한 듣기는 그 일을 건너뛰고 '시작' 알림만 바로 옵니다. 10-22 기록에서 WebKit 의 start 사건과 audiostart 는 성공 · 실패 모두 같은 ms 에 옵니다(3082~3089 '같은 ms').
- **코드 쪽**: 앱은 듣기마다 새 객체를 만들고 누름 처리 안에서 동기로 start 를 부릅니다(`browser.ts:321-334`, `child-turn.tsx:435-444`, `follow-along.tsx:297-301`). as 는 그 start 호출과 WebKit 의 audiostart 사이 시간이라서, 앱 코드가 as 를 줄일 길은 없습니다. 앱이 세션 꼴을 바꾸지 않는다는 것도 맞습니다. src 의 audioSession 은 관찰 쪽에만 있습니다(`teacher.ts:7`, grep 결과).
- **기전(추정)**: WebKit 이 입력 경로가 이미 켜져 있다고 보고 다시 설정하지 않지만, 실제 입력은 오지 않는 상태로 보입니다. 이 상태는 새 객체에도 이어지고(표 B), 가끔 저절로 풀립니다(표 C). WebKit 내부 동작은 이 저장소 자료로 확인하지 못했습니다.

### H2(2순위, 10-22 에서 확인 · 11-05 · 11-06 에서는 미확인): 앞 객체 end 직후 누름 밖에서 연 새 객체가 그 상태를 만든다

- **근거**: 10-22 auto 꼴에서 성공 다섯 번 뒤, 상태 기계의 끊어 듣기 재시작이 end 2ms 뒤에 새 객체를 열었습니다. 그 객체부터 소리가 끊겼고 뒤의 누름 듣기 둘도 실패했습니다(3224~3262줄). 그 앞 교대 넷은 듣기 끝 0~1ms 뒤 읽어 주기, 그 뒤 1.5~2초에 누름이었는데 모두 성공했습니다(3100~3192줄). 그러므로 '읽기 직후 듣기'보다 '끝 직후 누름 밖 start'가 들어감 사건과 맞습니다.
- **앱에서 같은 꼴을 만드는 길**: `listen.ts:445-447`(끊어 듣기 멈춤 뒤 end 에서 바로 restart), `508-513`(브라우저가 스스로 끝냈고 글이 있으면 바로 restart), `530-537`(글이 있는 no-speech 에서 abort 뒤 같은 차례 restart), `469`(감시 타이머 restart)입니다. 모두 `browser.ts:321-334` 에서 그 자리에서 새 객체를 start 합니다.
- **11-05 · 11-06 에 닿는가**: 3단계 대화 규칙은 끝 조용함 3초 · 상한 15초 · 끊어 듣기 15초입니다(`core/conversation/listen.ts:74-78`, `seed/settings.json:116 · 121`). 상한과 끊어 듣기가 같은 때라 `onTimer` 가 상한을 먼저 고르므로(`listen.ts:477-479`) 끊어 듣기 재시작은 없습니다. 실패 듣기 길이도 2.8~6.1초라 감시 재시작(18초)도 없습니다. 브라우저 스스로 끝 재시작은 일어날 수 있지만, 요약 칸에 재시작 수가 없어 확인하지 못합니다(`listen-log.ts:113-147` 는 첫 객체의 as 만 남김). 따라서 11-05 · 11-06 의 들어감 사건은 열린 물음입니다.
- **앞으로의 영향(확인됨)**: 8단계부터 대화(talk_long, 끊어 듣기 15초 · 상한 talk.max_answer_seconds)와 두 문장 이상 말하기 답은 15초마다 이 재시작을 일상으로 거칩니다(`core/conversation/listen.ts:66-72`). 10-22 기록대로라면 iPad 에서 긴 답 하나가 뒤의 듣기를 막을 수 있습니다(8절 U3).

### H3(3순위, 추정): 읽어 주기의 재생 상태가 녹음 상태로 바뀌지 못한 채 start 가 불린다

- **근거**: C109 의 playback 꼴 실패가 같은 꼴입니다. 앱은 대화 차례 누름마다 `speechSynthesis.cancel()` 을 부른 뒤 start 합니다(`talk-frame.tsx:1672-1675` → `tori.tsx:837-845` → `browser.ts:177-180`). 감시 상한이 끝낸 발화도 `synth.cancel()` 로 거둡니다(`browser.ts:481-491`).
- **반대 근거**: 읽기 뒤 경과(tc)로 갈리지 않습니다. cancel 을 부르지 않는 쪽지 길(`follow-along.tsx:291-301`)도 실패했고, cancel 을 부르는 대화 길도 성공이 있습니다. 10-22 교대 넷은 읽기 직후에도 성공했습니다.
- **가를 자료**: start 때 `speechSynthesis.speaking · pending`, 앞 읽기가 끝 알림 · 감시 상한 · 취소 가운데 무엇으로 끝났는지입니다. 감시 상한은 이미 `client_listen.sp`(끝 알림 없음 · 들려주지 못함)로 서버에 있습니다(`client-listen.ts:55-58 · 72`). 11-06 표에는 이 칸이 없어 10절에 열린 물음으로 둡니다.
