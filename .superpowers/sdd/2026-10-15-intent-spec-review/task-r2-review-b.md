## 1부 — 기술 · 데이터 · AI · 운영(1회차와 같은 범위)
- 수업 · 문제 · 평가 문항이 개발 때 시드로 바뀐 뒤의 데이터 모델: 시드 → DB 적재 방식, 판 번호, 진행 중 세션과 새 판의 관계, 테이블 수와 열이 6절 · 11절 · 14절과 맞는지, 삭제된 생성 · 버퍼 흔적이 남았는지.
- 실시간 호출만 남은 6절: 회화 턴(Sonnet · 흘려 보내기 · 읽어 주기)의 응답 시간 목표와 실패 처리, 흘려 보내는 글과 Zod 검증의 순서(검증 전 글이 아이에게 보이는 문제), 토리 규칙(개인정보 질문 금지 · 금지어)을 어디서 어떻게 거르는지.
- 상한을 없앤 비용 모델: 하루 평균 사용량 가정 두 가지가 현실적인지, 안전 상한 기본값이 사고를 막을 만큼 낮고 정상 사용을 막지 않을 만큼 높은지, 부모 알림의 시점 · 채널.
- 개인정보: 회화 대화 기록(원문 12개월 보관), 지난 대화 요약 · 친한 정도의 저장 범위, 아이에게 고지하는 문구, 부모 열람.
- 음성: 토리 읽어 주기(TTS)와 아이 음성 인식의 브라우저 지원 · 실패 시 글자 입력 전환, 태블릿에서의 제약.
- 접근 제어 · RLS · 서버 전용 키가 새 화면(수업 목록 · 배치 평가 · 회화)에도 그대로 적용되는지. 테스트(9절)가 새 FR · AC 를 다 덮는지.
- Next.js 16 · React 19 · Drizzle · Anthropic SDK(structured outputs · streaming) 사실 확인이 필요한 문장.

## 2부 — 수업 생성과 관리. 보고서에 별도 절 "수업 생성과 관리"로, 번호는 B2-M-
요청자 지시(2026-10-15 10:34 "수업 생성과 관리 … 추가로 체크")로 더한 부분이다. 1부와 섞지 말고 따로 절을 두되, 깊이는 1부와 같게 한다. 만드는 사람 · 고치는 사람 · 운영하는 사람(요청자 한 사람)의 눈으로 본다.

수업 · 문제 · 단계 평가 문항 · 배치 평가 문항 · 회화 시나리오 카드가 개발 때 시드로 만들어진다. 요청자 한 사람이 운영한다고 보고 아래를 본다.
- 만들기: 영역 4 × 12단계 × 단원 5 × 수업 13회(약 3,120)와 관심 주제 변형을 어떤 순서 · 묶음으로 만들고, 어떻게 검증하고(6.4 검증기), 검증에 떨어진 것을 어떻게 고치는지가 문서에 있는가. 비용 · 시간 추정이 있는가. Claude Code 세션으로 만들 때와 Batch 로 만들 때 품질 · 일관성(같은 단계 안에서 난이도 흔들림)을 어떻게 맞추는가.
- 관리: 잘못된 수업(오답 · 부적절 내용 · 밴드 밖 단어)을 부모나 아이가 발견하면 어떻게 알리고 고치는가. 판 번호를 올릴 때 진행 중 아이에게 무슨 일이 생기는가. 시드 파일 크기 · 저장소 · DB 적재 · 배포 순서. 회화 시나리오 카드가 3,120 수업과 같은 틀인가 다른 틀인가.
- 부모 미리보기: 시드 전체를 부모가 볼 수 있다는 말이 화면으로 가능한가(수천 건). 다음 단원 미리보기의 실제 모습.
- 빠진 역할: 생성 파이프라인을 지우면서 함께 사라진 기능(보강 수업 즉석 생성 · 재생성 · 관심 주제 즉시 반영)을 무엇으로 대신하는지가 적혀 있는가.
