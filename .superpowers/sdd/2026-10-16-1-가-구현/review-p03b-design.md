# 화면 검토 보고: 접근 코드 화면(P3b, design-reviewer · Opus · xhigh)

대상은 워크트리 `.claude/worktrees/agent-a4f928c00fc43a1e8` 의 `src/app/(setup)/access/` 세 파일과 e2e 사진 `p03b-access.png`(WebKit 820 × 1180, 2배율)이다. 첫 검토라 앞선 열린 항목은 없다.

사진 한 장은 빈 첫 화면뿐이라 상태별 화면을 따로 찍었다. 워크트리의 기존 빌드(BUILD_ID 21:33, 화면 파일 21:20 보다 뒤)를 3199 포트로 띄우고, 스크래치패드의 Playwright 스크립트로 WebKit(iPad Pro 11 장치값, 820 × 1180)과 Chromium(820 × 1180)을 돌렸다. 제출 응답은 `page.route` 로 401 · 429 · 503 · 연결 끊김을 흉내 냈다. 장부 사진은 덮어쓰지 않았고, 근거 사진 셋을 이 폴더에 `p03b-design-*.png` 로 남겼다. 코드는 고치지 않았다.

## 지적

### I1. Important. Chromium 에서 입력칸 · 버튼의 초점 표시가 거의 보이지 않는다
- 자리: `src/app/globals.css:120`(`* { @apply border-border outline-ring/50; }`)이 브라우저 기본 초점 고리 색을 회색 50% 투명으로 바꾼다. 입력칸 `access-code-form.tsx:71` 과 버튼 `:77` 에는 `focus-visible:` 꾸밈이 없다. shadcn 기본 바탕은 자기 부품이 따로 초점 고리를 그린다고 보고 이 줄을 둔다. 이 화면은 shadcn 부품이 아닌 맨 요소라 그 고리가 없다.
- 실측: Chromium 에서 Tab 으로 초점을 옮기면 입력칸 · 버튼 모두 `outline: auto 1px oklab(0.708 0 0 / 0.5)` 다. 흰 바탕 위에서 약 1.5 : 1 이다. 사진 `p03b-design-chromium-focus-input.png` 는 초점 전 테두리와 거의 구별되지 않고, `p03b-design-chromium-focus-button.png` 는 검은 버튼 둘레에 1px 옅은 선뿐이다. WebKit 은 auto 고리에 글쓴이 색을 쓰지 않아 입력칸에 파란 고리가 또렷하다(iPad Safari 는 문제없음).
- 근거: 브리프 기준 3 '초점 · 대비'. WCAG 2.2 1.4.11(비텍스트 대비, AA)은 초점 상태를 알아보게 하는 표시에 3 : 1 을 요구한다(W3C Understanding 1.4.11, 널리 확인된 사실). 대상 브라우저에 Android Chrome · Windows Edge 가 있다(`specs/11-요구사항과-수용-기준.md:153` AC-N3). 실제 Edge · Android Chrome 실기는 확인하지 못했고 Playwright Chromium 으로만 쟀다.
- 고치는 법: 입력칸과 버튼에 `focus-visible:outline-4 focus-visible:outline-offset-2 focus-visible:outline-neutral-900` 처럼 진한 실선 고리를 단다. 전역 줄은 shadcn 몫이라 그대로 두고, P10 의 아이 화면 공통 초점 꾸밈이 생기면 그쪽으로 옮긴다.

### M1. Minor. 입력칸 테두리 대비가 3 : 1 에 못 미친다
- 자리: `access-code-form.tsx:71` `border-neutral-400`(oklch 0.708). 흰 바탕과 약 2.6 : 1 이다. 사진의 입력칸 테두리가 옅다.
- 근거: 브리프 기준 3 '대비', WCAG 1.4.11(입력칸 경계 3 : 1). 이름표가 바로 위에 있어 칸을 못 찾을 정도는 아니라 Minor 다.
- 고치는 법: `border-neutral-500`(약 4.7 : 1) 또는 더 진한 값.

### M2. Minor. 입력칸 `required` 가 정본 밖 브라우저 문구를 띄운다(plan-p03b 197줄 '검토자 판정' 항목)
- 자리: `access-code-form.tsx:68`. 구현 보고 '설계와 다르게 한 것' 3.
- 실측: 빈 칸으로 '들어가기'를 누르면 앱 문구가 아니라 브라우저 말풍선이 뜬다. 문구는 브라우저 UI 언어를 따른다. Playwright WebKit 은 'Fill out this field', Chromium 은 'Please fill out this field.' 였다. 한국어로 설정된 실제 iPad 에서 어떤 문구가 뜨는지는 확인하지 못했다.
- 근거: 4절 '앱의 안내 · 버튼은 해요체'(`specs/03-화면.md:7`). 이 화면의 문구는 C57 일곱으로 정했다(`specs/10-결정-기록.md:207`). 말풍선은 그 밖의 문구이고 해요체도 영어 여부도 앱이 정하지 못한다. 덧붙여 공백만 넣으면 `required` 를 지나고, 끝점이 앞뒤 공백을 지운 빈 코드도 실패 한 번으로 센다(`submit/route.ts:44` 의 trim 뒤 `attempts.ts` 의 (바)). 그래서 구현자가 든 목적도 다 이루지 못한다. 셈 쪽은 code-reviewer 몫이라 화면 판정만 적는다.
- 고치는 법: `required` 를 빼고 `onSubmit` 첫머리에서 `code.trim()` 이 비면 요청 없이 입력칸에 초점만 두고 돌아간다. 새 문구가 필요 없다.

### M3. Minor. 버튼으로 제출하면 초점이 문서 밖(body)으로 빠지고 돌아오지 않는다
- 자리: `access-code-form.tsx:76`(기다리는 동안 `disabled`), `:43-51`(응답 뒤 초점을 다루지 않음).
- 실측: 두 엔진 모두 버튼을 눌러 401 을 받으면 `document.activeElement` 가 BODY 다. 입력칸은 비워졌는데 초점이 없어, 키보드 사용자는 처음부터 Tab 을 다시 눌러야 한다. 입력칸에서 Enter 로 제출하면 초점이 입력칸에 남는다(두 엔진 확인).
- 근거: 브리프 기준 3 '초점 차례', WCAG 2.4.3(초점 순서). iOS 는 사용자 동작 밖의 `focus()` 로 화면 자판을 띄우지 않는다고 알려져 있어(확인 정도 중간) iPad 에서는 다시 누르기가 남는다. 그래서 Minor 다.
- 고치는 법: 입력칸에 ref 를 달고 204 가 아닌 모든 결과 뒤에 `inputRef.current?.focus()` 를 부른다.

### M4. Minor. 끊김 문구의 출처가 '8절'로 적혔는데 문구는 7절에 있다
- 자리: 4절 접근 코드 행 `specs/03-화면.md:13` '끊김은 8절 문구', C57 `specs/10-결정-기록.md:207` '끊김은 8절', plan-p03b 값 8(99줄), 코드 주석 `access-code-form.tsx:3` · `:10`.
- 근거: '인터넷이 끊겼어요. 연결되면 다시 해요'는 7절 음성 처리 표의 네트워크 행(`specs/07-음성과-오류.md:33`)에만 있다. 8절은 36줄부터이고 그 '네트워크 끊김' 행(67줄)에는 화면 문구가 없다. 화면에 나온 글자는 7절 문구와 같다.
- 고치는 법: 참조를 '7절 네트워크 행 문구'로 바꾸거나, 8절 '네트워크 끊김' 행에 이 문구를 앱 공통 끊김 안내로 더한다. 정본을 고치는 일이라 컨트롤러 몫이다. 코드 주석은 그 결정에 맞춘다.
