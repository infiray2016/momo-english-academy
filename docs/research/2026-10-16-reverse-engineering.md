# 리버스 엔지니어링은 무엇이고 우리 프로젝트는 어디에 쓰나 (2026-10-16 조사)

요청자가 2026-10-16 03:3x 에 "AI SDLC, 그래프 엔지니어링, 리버스 엔지니어링을 활용해 프로젝트를 개발할 것이다. 잘 모르면 심층 조사해서 옵시디언에 저장하고 프로젝트에서 활용 가능하도록 구성해야 한다"고 했고, 컨트롤러 지시로 조사 담당이 리버스 엔지니어링(reverse engineering)을 맡았다. 질문은 셋이다. 이 말은 정확히 무엇을 가리키는가. 어디까지 해도 되고 어디부터 안 되는가. 우리 프로젝트의 어느 일에 쓰는가. 어제 한 `2026-10-15-program-reverse-engineering.md` 는 아래 분류로 보면 제품 분해(teardown) 가운데 '공개 자료만 읽는' 형태다. 공식 페이지 · 도움말 · 과정표 · 가격표만 읽었고, 제품을 직접 쓰지도, 통신을 보지도, 코드를 열지도 않았다. 그래서 직접 써 봐야 아는 것이 '확인 못 함'으로 남았다. 이번에는 그 바깥까지 포함해 갈래 여섯을 놓고, 방법과 도구, 법 · 윤리의 선, 우리 프로젝트에 쓸 제안 열 가지, 스킬 뼈대를 적었다. 코드 관계도(code graph)는 `2026-10-16-graph-engineering.md` 가 다루므로 한 줄만 짚는다. 법 조문과 판결은 원문이나 공식 요약으로 확인했지만 이 문서는 법률 자문이 아니다. 표마다 확인 정도를 원문 · 검색 요약 · 추정으로 나눴고 출처는 끝에 모았다.

## 한 줄 결론

리버스 엔지니어링은 이미 있는 것을 살펴 구성 요소와 관계를 알아내고 더 높은 추상으로 다시 그리는 일이다. 정의상 **살펴보는 일이지 고치거나 복제하는 일이 아니다**(Chikofsky · Cross 1990). 우리에게 쓸 곳은 넷이다. 참고 서비스를 직접 써 보며 분해하기, 쓰는 외부 API와 브라우저 기능을 실제로 불러 보며 확정하기, 코드가 생긴 뒤 코드에서 spec 을 되짚어 정본과 어긋난 곳 찾기, 시드를 아이 눈으로 분해하기다. 선은 분명하다. 공개 자료 읽기와, 내 기기 · 내 계정 · 내 키로 정상 이용하며 보는 것은 한다. 프로그램 디컴파일, 보호 조치 우회, 남의 서버에 자동 요청, 남의 문장 · 그림 · 음원 복사, 아이나 타인 계정 사용은 하지 않는다. 한국 저작권법이 허락 없는 프로그램 코드 역분석을 열어 둔 것은 다른 프로그램과의 호환에 필요한 부분 하나뿐이라, 경쟁 분석은 이 예외에 기댈 수 없다.

## 리버스 엔지니어링이 가리키는 여섯 용어

1990년 Chikofsky 와 Cross 가 뒤섞여 쓰이던 말을 여섯으로 갈라 정리했다. 지금도 이 구분이 기준이다. 세 단계(요구 · 설계 · 구현)의 추상 수준 위에서 어느 방향으로, 무엇을 바꾸며 움직이는가가 갈린다.

| 용어 | 원문 정의의 요지 | 대상을 바꾸나 | 우리에게 |
|---|---|---|---|
| 앞으로 가는 개발(forward engineering) | 높은 추상(요구, 구현과 무관한 설계)에서 실제 구현으로 내려가는 보통의 개발 | 새로 만든다 | intent → spec → plan → 코드 사슬이 이것이다 |
| 리버스 엔지니어링 | 대상 시스템의 구성 요소와 서로의 관계를 찾고, 다른 모양이나 더 높은 추상으로 표현을 만든다. 수명주기 어느 단계에서 시작해도 된다 | 바꾸지 않는다. 살펴보는 과정이지 바꾸거나 복제하는 과정이 아니다 | 이 문서의 주제 |
| 문서 다시 만들기(redocumentation) | 같은 추상 수준에서 뜻이 같은 다른 표현을 만들거나 고친다. 사람이 읽을 용도(데이터 흐름도, 구조도, 상호 참조 목록). 가장 단순하고 오래된 형태 | 바꾸지 않는다 | 코드에서 식별자 표를 뽑아 정본과 맞대기 |
| 설계 복원(design recovery) | 코드에 영역 지식, 코드 밖 자료, 추론을 더해 코드만 봐서는 얻을 수 없는 높은 추상을 알아낸다. 무엇을 · 어떻게 · 왜까지 | 바꾸지 않는다 | '왜'는 코드에 없다. 우리는 13절 결정 기록이 맡는다 |
| 구조 다듬기(restructuring) | 같은 추상 수준에서 모양만 바꾸고 바깥 동작은 그대로 둔다 | 모양만 바꾼다 | 코드 정리 |
| 고쳐 짓기(reengineering) | 리버스 엔지니어링을 한 뒤 앞으로 가는 개발이나 구조 다듬기로 새 모양을 만든다. 새 요구를 넣을 수 있다. 앞의 둘의 상위 개념은 아니다 | 바꾼다 | 해당 없음 |

확인 정도는 원문이다. 논문은 끝에서 이 도구들이 앞으로 완성된 모든 시스템을 의도한 설계에 견주어 검증하는 데 쓰일 것이라고 적는다(원문을 우리말로 옮겼다). 정본 spec 과 코드를 맞대는 우리 제안 6~8번이 이 문장과 같은 쓰임이다.

## 갈래마다 무엇을 하나

대상이 무엇이냐로 나누면 갈래가 여섯이다. 앞의 여섯 용어는 일의 성격을 가르고, 이 표는 일감을 가른다.

| 갈래 | 무엇을 보고 무엇을 얻나 | 대표 방법 | 우리와의 거리 | 확인 |
|---|---|---|---|---|
| 제품 분해(teardown) | 쓸 수 있는 제품의 기능 · 설계 선택 · 사용 경험 · 전략을 뜯어, 무엇을 하는지보다 어떻게, 왜 그렇게 만들었는지를 알아낸다. 산출은 화면 흐름 지도, 기능표, 가격표, 가설이다 | 제품 고르기 → 범위 정하기 → 자료 모으고 분석 → 기록 → 종합과 권고 다섯 걸음(LogRocket) | 가깝다. 어제 조사는 이 갈래의 '공개 자료만' 형태였다 | 원문(절차), 검색 요약(정의) |
| 통신 관찰과 프로토콜 복원(network observation) | 웹이나 앱이 서버와 주고받는 요청 · 응답을 기록해 주소, 매개변수, 응답 모양, 순서 규칙을 알아낸다 | 브라우저 개발자 도구, HAR 파일, 가로채기 프록시 | 가깝다. 우리가 쓰는 API 를 보는 일에 쓴다. 경쟁 서비스 서버는 법 · 약관 선이 있다 | 원문 |
| 코드 리버스 엔지니어링 | 컴파일된 프로그램을 분해해 사람이 읽는 코드나 동작을 얻는다. 디컴파일, 디스어셈블, 바이너리 분석, 실행 중 후킹이 여기에 든다 | Ghidra, jadx, Frida | 멀다. 한국에서 허락 없이 되는 것은 호환 목적뿐이다 | 원문 |
| 소프트웨어 고고학(software archaeology) | 남이 짠(또는 지난 내가 짠) 코드를 이해한다. 코드는 짠 순간부터 물려받은 코드가 된다. 현장 점검(필요한 소스가 다 있나), 현장 보호(버전 관리 · 반복 가능한 빌드), 지도 그리기, 용어집, 실행 추적, 위에서 내려다보기, 이름과 주석을 믿지 말고 테스트로 증명하기, 그때 그 사람은 무슨 생각이었나 따져 보기 | 검색 · 색인, 손으로 그린 지도, 용어집, 추적 | 코드가 생긴 뒤. 1차 구현 뒤 차수마다 | 원문 |
| 명세 복원(코드 → 문서 · 테스트) | 문서 다시 만들기, 설계 복원, 동작 기록 테스트(characterization test, 골든 마스터 · 스냅샷 테스트라고도 부른다)를 합친다. Feathers 는 목적을 시스템의 실제 동작을 문서로 남기는 것이라 한다. 틀린 기대값으로 테스트를 쓰고, 실패 메시지에서 실제 값을 받아 기대값으로 넣고, 이름을 고치고, 설명 안 되는 동작은 버그로 단정하지 말고 기록해 둔다 | 식별자 표 뽑기, 규칙 목록 쓰기, 동작 기록 테스트 | 가깝다. spec ↔ 코드 동기화의 몸통이다 | 원문(Feathers · 논문), 검색 요약(별칭) |
| AI 에이전트가 하는 복원 | 에이전트가 저장소를 읽어 구조 설명 · 사용자 이야기 · 업무 규칙 · spec 을 만든다. 연구 결과는 바로 아래 표에 모았다 | 개요 → 구조 → 자료 모형 → 용어집 질문(Claude Code), 읽기 전용 에이전트, 코드와 문서를 잇는 연결 표 | 가깝다. 우리 작업 방식이 이미 이 갈래다 | 원문(Claude Code), 검색 요약(논문 초록) |

AI 에이전트 복원 연구 결과는 숫자가 있어 표로 따로 둔다. 모두 초록만 읽었다.

| 연구 | 한 일 | 결과 |
|---|---|---|
| arXiv 2509.19587 | 코드 조각 1,750개에서 사용자 이야기를 복원, 모델 다섯 | 코드 200줄 이하에서 평균 F1 0.8 |
| arXiv 2603.21178 | 저장소 340개에서 구조 뷰 4,137개 생성 | 문법은 맞지만 구조 추상이 아니라 코드 수준에 머문다. 사람이 필요하고 에이전트는 보조 도구다 |
| arXiv 2609.03721 | 커밋에서 설계 결정을 뽑게 함, 모델 넷 | 점수는 높으나 결과가 길고 구현 중심이며 결정의 이유가 빠진다 |
| arXiv 2610.20068 | 의도만 줬을 때와 복원한 요구 · 구조 문서를 더 줬을 때를 견주며 에이전트가 라이브러리 29개를 다시 짬 | 시험 통과율은 33.7% 대 35.8% 로 유의한 차이가 없고, 모듈 구조 일치(F1)는 0.54 에서 0.63 으로 유의하게 가까워짐 |

| arXiv 2511.05165 | 코드에서 구성 요소도와 상태도를 뽑고 LLM 으로 핵심 요소를 거름 | 사람 전문가 의존을 줄이는 반자동 방식이라고 보고 |

이 표에서 우리가 가져갈 것은 둘이다. 복원문은 이유(왜)를 못 담으니 이유의 정본은 13절 결정 기록으로 둔다. 복원문의 모든 주장에 코드 위치와 확신도를 달고, 근거 없는 줄은 빈칸으로 남겨 사람이 정한다.

## 방법과 도구

이름과 쓰임만 적는다. 우리가 쓰지 않을 것도 무엇을 하는 도구인지는 알아 두려고 넣었다.

| 대상 | 방법 | 도구와 쓰임 | 알아 둘 점 | 확인 |
|---|---|---|---|---|
| 웹 앱 통신 | 브라우저 개발자 도구의 네트워크 탭에서 요청을 보고, HAR 파일(HTTP Archive, 브라우저가 주고받은 요청을 JSON 으로 적은 파일)로 내보낸다 | Chrome 개발자 도구 | Chrome 은 기본으로 Cookie · Set-Cookie · Authorization 헤더를 뺀 'sanitized' 내보내기를 하고, 설정(Allow to generate HAR with sensitive data)을 켜야 비밀값이 든 파일이 나온다 | 원문 |
| 웹 · 앱 통신 가로채기 | 기기를 프록시에 물려 요청과 응답을 가로채 보고, 고치고, 저장하고, 다시 재생한다 | mitmproxy. 콘솔 · 웹 · 명령줄 세 가지 모양. HTTP/1 · HTTP/2 · WebSocket | HTTPS 를 보려면 프록시가 만든 인증서를 기기에 깔아야 한다. 인증서 고정(certificate pinning, 앱이 믿을 서버 인증서를 미리 정해 두는 방식)을 쓰는 앱은 앱을 고쳐야 가로챌 수 있다고 문서가 적는다. 그 수정은 보호 조치 우회에 닿는다(법 · 윤리 표) | 원문 |
| 통신 기록해 되살리기 | 진짜 통신을 파일에 기록해 두었다가 시험에서 되살린다 | Playwright 의 `routeFromHAR`. `update` 를 켜면 기록, 끄면 재생 | 재생은 URL · 메서드가 같아야 하고 POST 는 본문도 맞아야 한다. 브라우저 밖 서버가 부르는 외부 API 는 이 방법이 못 잡는다 | 원문 |
| 서버가 부르는 외부 API | SDK 의 fetch 를 바꿔 끼우거나, 응답을 `.withResponse()` 로 받아 상태 · 헤더 · 요청 번호를 저장한다 | Anthropic TypeScript SDK 의 `fetch` · `fetchOptions` · `_request_id` · `logLevel` | `logLevel: "debug"` 는 요청 · 응답의 헤더와 본문을 모두 남긴다. 인증 헤더 일부만 가려지고 본문의 민감한 내용은 보일 수 있다고 문서가 경고한다 | 원문 |
| 모바일 앱 | 앱 파일을 풀어 읽고(jadx, 안드로이드 APK · dex 에서 자바 코드를 만든다), 디스어셈블 · 디컴파일하고(Ghidra, 미국 NSA 가 만든 분석 도구 모음), 실행 중인 프로세스에 코드를 넣어 함수를 가로챈다(Frida) | jadx, Ghidra, Frida. 안내서는 OWASP 모바일 앱 보안 시험 안내서(MASTG)의 '변조와 리버스 엔지니어링' | 우리는 쓰지 않는다. 쓰임만 안다 | 원문 |
| 코드베이스 | 코드를 질의할 수 있는 데이터베이스로 뽑아 묻는다(구문 트리 · 데이터 흐름 · 제어 흐름). 검색 · 지도 · 용어집 | CodeQL, grep · 색인 도구, 코드 관계도 | 관계도는 `2026-10-16-graph-engineering.md` 가 맡는다 | 원문 |
| 제품 분석 | 사용자 흐름 지도, 기능표, 가격표, 공개 문서(도움말 · 과정표 · 약관), 특허 | 브라우저 개발자 도구(화면 구조), 화면 기록 도구, 특허정보 검색 서비스 KIPRIS, 웹 보관소 | 웹 보관소는 이번에 열어 보지 않았다 | 원문(LogRocket), 검색 요약(KIPRIS), 추정(웹 보관소) |
| AI 에이전트 | Claude Code 공식 흐름은 개요 → 구조 패턴 → 핵심 자료 모형 → 용어집 순서로 넓게 묻고 좁혀 간다. 탐색이 길면 서브에이전트에 맡겨 주 대화를 깨끗하게 둔다. 기존 코드가 있는 개발(brownfield)의 명세 복원은 바꿀 것의 범위만 좁게 쓴다(지금 동작 · 목표 동작 · 바뀌면 안 되는 것 · 범위 밖) | Claude Code, 읽기 전용 분석가 에이전트 | 모든 주장에 코드 위치와 확신도를 단다 | 원문(Claude Code), 검색 요약(brownfield 글) |

## 법 · 윤리의 선

아래는 조문과 판결을 옮긴 것이고 법률 자문이 아니다. 한국은 저작권법 · 정보통신망법 · 개인정보 보호법 · 부정경쟁방지법이 겹친다. 미국과 EU 는 한국 판단의 참고로만 넣었다.

| 행위 | 한국 | 미국 · EU | 우리 규칙 | 확인 |
|---|---|---|---|---|
| 공개 자료 읽기, 정상 구독해 써 보기 | 저작권은 표현을 보호하고 사실과 방식은 보호하지 않는다는 일반 원칙이다. 단계 수 · 시간 · 가격 · 화면 흐름은 사실이고, 수업 문장 · 문항 · 음원 · 그림 · 화면 디자인은 표현이다. 프로그램에는 제101조의2 가 프로그램 언어 · 규약 · 해법에 이 법을 적용하지 않는다고 적는다 | EU 소프트웨어 지침 1조 2항은 프로그램의 바탕이 되는 아이디어와 원리를 저작권으로 보호하지 않는다고 적는다 | 한다. 분석 노트에는 사실과 구조만 쓰고 표현은 옮기지 않는다 | 조문은 원문. 사실과 표현의 구분은 일반 원칙이라 추정 |
| 약관이 막는 것 | 약관이 자동 수집 · 역분석 · 복제를 막을 때 법이 열어 둔 예외를 계약으로 없앨 수 있는지에 관한 한국 규정은 찾지 못했다. 대법원은 서비스 제공자가 접근을 제한했는지 가릴 때 보호조치와 이용약관 등 객관적 사정을 함께 본다고 했다 | EU 지침 8조는 6조(디컴파일)와 5조 2 · 3항(복사본 만들기, 관찰 · 연구 · 시험)에 어긋나는 계약 조항을 무효로 한다. 미국은 EFF 안내에 따르면 클릭으로 동의한 약관을 집행한 판결이 있고(Blizzard v. BnetD) 법이 분명하지 않다 | 분석을 시작하기 전에 그 서비스의 약관을 읽어 노트에 한 줄 남긴다. 자동 수집 · 역분석 · 캡처 · 계정 공유 금지 문구가 있으면 '쓰는 사람이 화면에서 보는 것'까지만 한다 | EU · 미국은 원문. 한국은 확인 못 함. 경쟁 서비스 약관 원문은 이번에 읽지 못했다 |
| 프로그램 코드 역분석(디컴파일) | 저작권법 제101조의4 제1항. 정당한 권한으로 프로그램을 쓰는 사람이나 그 허락을 받은 사람이, 호환에 필요한 정보를 쉽게 얻을 수 없고 얻는 것이 불가피할 때, 호환에 필요한 부분에 한해 허락 없이 역분석할 수 있다. 제2항은 얻은 정보를 호환 목적 밖에 쓰거나 제3자에게 주는 것, 표현이 실질적으로 비슷한 프로그램을 만드는 데 쓰는 것을 막는다. 서울중앙지법 2014.1.23.(2013가합23162, 확정)은 역분석이 복제를 수반하므로 허락 없이는 복제권 침해라고 보았다. 적법성 · 보안 적합성을 확인하려는 조사는 아이디어와 원리를 확인하는 기능 조사 예외(제101조의3 제1항, 판결 당시 제6호)에 해당하지 않고, 기술 지원을 먼저 요청할 수 있었는데 하지 않았다는 점을 따졌으며, 공정 이용 일반론으로 예외를 넓히지 않았다 | 미국 DMCA 1201조 (f)는 합법적으로 쓸 권리를 얻은 프로그램의 접근 통제를 우회해, 독립적으로 만든 프로그램과의 상호 운용에 필요한 요소를 식별 · 분석하는 일을 풀어 주고, 그 수단과 얻은 정보도 상호 운용 목적에 한해 만들고 나눌 수 있게 한다. 공정 이용 판례로 Sega v. Accolade, Sony v. Connectix 가 있다. EU 지침 6조는 이용 권한자일 것, 정보를 쉽게 구할 수 없을 것, 필요한 부분에 한정할 것 세 조건으로 호환 목적 디컴파일을 허용하고, 5조 3항은 프로그램을 실행하면서 관찰 · 연구 · 시험하는 것을 허락 없이 허용한다 | 하지 않는다. 우리는 경쟁 앱과 호환할 프로그램을 만들지 않으므로 어느 예외에도 맞지 않는다 | 원문 |
| 통신 관찰과 서버 자동 요청 | 대법원 2022.5.12. 선고 2021도1533. 경쟁사 앱의 API 서버 주소와 명령을 패킷 캡처 등으로 알아내 크롤링한 사건에서 정보통신망 침해 · 데이터베이스제작자 권리 침해 · 컴퓨터등장애업무방해가 모두 무죄로 확정됐다. 주소와 명령을 쉽게 알 수 있었고 별도 접근 차단이 없었으며 수집한 정보 대부분이 공개된 것이라고 보았다. 해설은 이것이 크롤링 일반을 허용한 판결이 아니라고 본다. 민사에서는 부정경쟁방지법 (파)목(성과 도용)과 정보통신망법 위반 주장의 비중이 커질 것이고, 명시적 금지 문구나 유료 회원 ID 로 수집한 경우를 사전에 점검하라고 권한다 | 이번에는 찾지 않았다 | 남의 서비스 서버에 우리가 자동으로 요청을 보내는 일은 하지 않는다. 우리 키로 우리가 쓰는 외부 API 를 부르며 그 통신을 보는 일은 남의 서비스를 뜯는 것이 아니라 내 요청의 응답을 보는 것이라 한다 | 원문(해설), 검색 요약(대법원 요지). 마지막 규칙은 해석이라 추정 |
| 보호 조치 우회 | 저작권법 제104조의2 제1항. 정당한 권한 없이 기술적 보호조치를 제거 · 변경 · 우회해 무력화하는 것을 막는다. 단서의 예외 여덟 가운데 호환을 위한 프로그램코드역분석(제6호)과, 정당한 권한을 가진 사람이 오로지 컴퓨터나 정보통신망의 보안성을 검사 · 조사 · 보정하는 경우(제7호)가 눈에 띈다. 앞의 서울중앙지법 판결은 라이선스 확인 기능을 지운 것을 기술적 보호조치 무력화로, 회사명이 든 홈페이지 주소와 패키지명을 지운 것을 권리관리정보 제거로 보았다 | 미국 1201조 (a)(1)(A)는 저작물 접근을 통제하는 기술 조치의 우회를 금지한다. EFF 는 인증 절차, 코드 서명, 난독화, 프로토콜 암호화에도 미칠 수 있다고 본다 | 하지 않는다. 로그인 · 유료 벽 · 인증서 고정 · 라이선스 확인 · 난독화를 건드리지 않는다. 자동 접근을 막은 사이트는 우회하지 않고 사람이 브라우저로 본다 | 제6호 · 제7호는 원문, 나머지 호는 요약 |
| 클린룸 방식과 특허 | 클린룸 방식을 직접 다룬 한국 판결은 찾지 못했다 | 분석 팀이 대상을 살펴 기능 명세서를 쓰고(법률가가 저작물이 섞였는지 검토), 대상을 본 적 없는 다른 팀이 명세서만으로 구현한다. 독립 창작이라 저작권 방어가 되지만 특허는 막지 못한다. Phoenix 가 IBM PC 호환 BIOS 를 이렇게 만들어 팔았다. Sony v. Connectix 항소심은 BIOS 동작을 알아내는 데 디스어셈블이 필요했다고 인정했다 | 경쟁 서비스를 본뜰 계획이 없으므로 클린룸을 돌릴 일은 없다. 원칙만 가져온다. 분석 노트(사실과 구조)와 우리 spec(우리 표현)을 나누고 노트의 문장을 spec 에 그대로 옮기지 않는다. 특이한 학습 방법이 눈에 띄면 KIPRIS 에서 한 번 찾아 둔다 | 원문(Wikipedia, EFF), 검색 요약(KIPRIS) |
| 개인정보와 비밀값 | 개인정보 보호법 제22조의2. 만 14세 미만 아동의 개인정보를 처리하려고 동의를 받아야 할 때는 법정대리인의 동의를 받고 동의했는지 확인해야 한다. 어기면 5년 이하 징역이나 5천만 원 이하 벌금에 처할 수 있다는 해설이 있다 | 이번에는 찾지 않았다 | 통신 기록(HAR · 프록시 흐름 · SDK debug 로그)에는 쿠키 · 토큰 · 키 · 이름이 든다. 관찰은 시험 계정 · 시험 키 · 어른이 읽는 시험 문장으로만 한다. 가족 접근 쿠키 · 아이 이름 · 아이 목소리를 기록 파일에 넣지 않는다. 기록 파일은 저장소에 올리지 않고 필요한 표본은 비밀값을 지운 고정 표본으로만 올린다. 남의 계정 · 아이 계정으로 서비스를 쓰지 않는다. 비밀값과 아이 이름을 대화에 적지 않는 CLAUDE.md 규칙과 같은 방향이다 | 검색 요약(조문 본문과 해설) |

### 공개 자료 기반 분석과 바이너리 역분석의 차이

두 일의 차이는 복제가 끼느냐다. 공개 자료를 읽는 것은 읽을 뿐이라 복제가 없다. 프로그램 파일을 분해하는 것은 프로그램을 복제하고 변환해야 하므로 서울중앙지법 판결이 말한 대로 법이 따로 열어 준 예외가 있어야 한다. 그 사이에 있는 일들은 정상 이용의 연장인지, 서버를 건드리는지, 보호 조치를 건드리는지로 갈린다.

| 깊이 | 하는 일 | 복제 · 접근 | 법 · 약관 | 판정 |
|---|---|---|---|---|
| 1 | 공개 자료 읽기(공식 페이지 · 도움말 · 과정표 · 가격표 · 약관 · 특허) | 읽기뿐이라 복제가 없다 | 약관의 열람 제한만 본다 | 한다. 어제 했다 |
| 2 | 무료 체험이나 정식 구독으로 직접 써 보기(요청자 기기, 요청자 계정) | 정상 이용 | 약관의 캡처 · 녹화 · 계정 공유 금지 여부를 먼저 본다 | 한다. 아직 안 했다 |
| 3 | 화면 흐름 메모와 분석용 소량 캡처 | 정상 이용의 기록 | 약관 확인. 다시 퍼뜨리지 않고, 수업 문장 · 그림 · 음원은 옮기지 않는다 | 한다 |
| 4 | 우리가 쓰는 API · 브라우저 기능을 내 키와 내 기기로 관찰 | 내 요청과 응답을 본다 | 개인정보와 비밀값 규칙 | 한다 |
| 5 | 경쟁 서비스의 통신 관찰 | 자기 기기의 통신이지만 서버를 건드릴 위험이 있다 | 약관 · 보호 조치 · 부정경쟁 위험(2021도1533 해설) | 하지 않는다. 화면에서 이미 보이는 것 이상을 얻지 못한다 |
| 6 | 앱 분해 · 디컴파일 · 인증서 고정 우회 · 자동 수집 · 유료 벽 우회 | 복제를 수반하거나 보호 조치를 건드린다 | 제101조의4 밖이고 제104조의2 에 걸린다 | 하지 않는다 |

## 우리 프로젝트에 비추면

리버스 엔지니어링은 우리에게 새 일이 아니다. 풀이 검사는 문항에서 정답을 거꾸로 짚는 일이고, 읽기 전용 분석가 에이전트는 코드와 정본을 맞대는 일이다. 여기에 이름과 선과 절차를 붙이고, 비어 있는 곳을 채우는 것이 이 절이다. AI SDLC 사슬에서 끼는 자리는 아래와 같다.

| 단계 | 리버스 엔지니어링이 하는 일 | 남는 곳 |
|---|---|---|
| Plan(intent) | 참고 서비스를 직접 써 보고 사실을 모아 요청의 근거와 제약으로 쓴다 | `docs/research/`, intent 의 제약 · 미결 사항 |
| Design(spec) | 쓰는 외부 API · 브라우저 기능의 실제 동작을 관찰해 가정을 확정한다 | 13절 결정 기록 한 줄, 고정 표본 |
| Build(plan) | 규칙을 바꾸기 전에 지금 동작을 기록하는 테스트를 둔다. 시드는 아이 눈으로 분해한다 | 테스트, 시드 보기 화면의 검토 기록 |
| Review | 코드와 시드에서 거꾸로 규칙을 뽑아 정본과 맞댄다 | 검토 보고 |

제안은 열 가지다. 비용 칸의 시간과 금액은 모두 조사 담당의 추정이고 잰 값이 아니다.

### 참고 서비스를 어디까지 더 분해할 수 있나

어제 조사의 '더 알아볼 것' 가운데 직접 써 봐야 풀리는 것은 다섯 묶음이다. 아동 AI 대화가 화면에 영어 문장을 보이는지(호두 · AI 펭톡). 한 대화의 턴 수와 말하는 양(호두의 '30분에 120문장'의 속). 윤선생 '최대 20회 반복'이 단어마다인지 문항 전체인지. 통과 문턱이 있는지. 리틀팍스 가정용 부모 보고, 호두 가격, EBS 두 서비스의 하루 분량, Lingokids 의 말하기와 복습. 앞의 깊이 표에서 깊이 2와 3까지가 닿는 범위다. 리얼 아카데미는 공식 사이트가 자동 접근을 막아 후기와 기사로만 정리했다(`2026-10-15-real-academy.md`). 막은 곳은 우회하지 않고 사람이 브라우저로 본다.

| 제안 | 하는 일 | 비용 | 효과 |
|---|---|---|---|
| 1. 직접 써 보기 질문표 | 위 다섯 묶음을 질문표로 바꿔, 서비스마다 요청자 기기와 요청자 계정으로 한 번씩 써 본다. 화면 흐름은 걸음마다 한 줄 메모와 소량 캡처로 남긴다. 아이 계정은 쓰지 않는다 | 서비스당 1~2시간과 이용권. 무료 체험이 있으면 이용권은 없다 | 어제 표에서 '바깥' 또는 '기준이 다름'으로 판정한 여덟 곳 가운데 회화 구조 · 통과 문턱 · 복습 양을 추정에서 직접 본 사실로 바꾼다 |
| 2. 가격과 구성의 시간 변화 | 공식 가격 · 이용권 페이지를 웹 보관소(Wayback Machine)의 옛 판과 견주어 개편을 날짜와 함께 적는다. 호두의 월 구독 전환은 블로그 글 하나로만 확인한 상태다 | 서비스당 30분 | 부모 안내의 "왜 이 가격 · 구성인가"와 13절 '다른 길' 까닭에 날짜 근거가 붙는다 |
| 3. 분해 노트 규칙과 하지 말 것 목록 | 노트에는 사실과 구조만 쓰고 표현을 옮기지 않는다. 약관을 먼저 읽어 한 줄 남긴다. 자동 수집, 앱 분해 · 인증서 고정 우회, 유료 벽 · 로그인 우회, 계정 공유 · 아이 계정, 수업 문장 · 문항 · 음원 · 그림을 시드로 가져오기, 자동 접근을 막은 사이트 우회는 하지 않는다 | 없음. 스킬 절차에 들어간다 | 법 · 약관 위험과 시드 저작권 문제를 처음부터 막는다 |

### 쓰는 외부 API와 브라우저 기능을 관찰로 확정하기

정본은 두 외부에 크게 기댄다. 음성 인식(7절의 브라우저 표)과 Anthropic API(5절 모델 조합 표, 8절 'AI 쉬는 중' 분류)다. 오늘 연 문서는 정본과 맞는다. MDN 호환표는 Chrome 139 부터 접두사 없는 SpeechRecognition 을, Safari 14.1 부터 webkit 접두사판을 적고 Firefox 는 미리보기뿐이다. 기기 안 인식(processLocally)은 Chrome · Edge 139 이상에만 있고, Chrome Android 는 `continuous` 를 받아도 효과가 없다. Chrome 인식은 소리를 웹 서비스로 보낸다. 다만 정본의 이 사실들은 문서에서 읽은 것이지 기기에서 본 것이 아니다. 문서가 메우지 못하는 곳이 둘 있다.

첫째, MDN 의 오류 값은 아홉 개인데 정본 7절이 다루는 것은 여섯 개(no-speech · aborted · audio-capture · network · not-allowed · service-not-allowed)다. 빠진 `language-not-supported` 는 MDN 이 브라우저마다 다르고 코드로 미리 확인할 수 없다고 적은 오류다. en-US 가 되는 기기인지는 기기에서만 안다.

둘째, Anthropic 오류 문서는 지출 한도 도달을 400 으로, 월 상한을 재시도 시간 헤더가 없는 429 로 적는다. 정본 8절의 진입 조건은 여기에 더해 400 문구와 429 의 오류 코드(enforced_spend_limit_reached)까지 가정한다. 이번에 연 오류 문서에는 문구와 오류 코드가 없고 별도 페이지에 있다고만 되어 있다. 실제 호출로 한 번 받으면 가정이 사실이 된다.

| 제안 | 하는 일 | 비용 | 효과 |
|---|---|---|---|
| 4. 음성 인식 이벤트 기록표 | 작은 관찰 페이지로 기기 · 브라우저마다 시작 · 소리 감지 · 중간 결과 · 최종 결과 · 끝 · 오류 이벤트와 시각을 기록한다. 1-가의 첫 작업인 iPad Safari 실기 확인을 같은 페이지로 한다. 마이크 거부 · 네트워크 끊기 · 말 안 하기를 일부러 일으켜 보고, en-US 에서 `language-not-supported` 가 나는 기기가 있는지 본다. 기록은 Playwright 가짜 음성 인식의 대본으로 되살린다. 어른이 시험 문장을 읽는다(Chrome 은 소리를 서버로 보낸다) | 관찰 페이지 반나절과 기기당 30분 | 가짜 API 가 실제 기기와 다르게 굴어 시험은 통과하는데 기기에서 깨지는 일을 줄인다 |
| 5. Anthropic 호출 관찰표 | 세 모델마다 호출 종류별(회화 턴 · 첨삭 · 확인 호출 등)로 시험 키와 시험 워크스페이스에서 한 번씩 불러 상태 · 헤더(요청 번호, 재시도 시간 유무) · 본문(usage · stop_reason · 내용 블록)을 비밀값을 가리고 파일로 남긴다. 특히 셋을 본다. 하나, 'AI 쉬는 중' 분류다. 시험 워크스페이스에 아주 낮은 지출 한도를 걸고 Haiku 1토큰 호출로 상태 · 오류 유형 · 문구 · 헤더를 받는다. 둘, 구조화 출력이다. 문서는 최솟값 · 최댓값 · 길이 제한을 문법에 싣지 못하고, stop_reason 이 refusal 이나 max_tokens 면 스키마와 안 맞을 수 있고, 열거값 대소문자가 달라질 수 있다고 적는다. Zod 의 어느 제약이 API 로 가고 어느 것이 서버 검증에만 남는지 호출로 확인한다. 셋, 모델별 요청 제약이다. 문서는 Sonnet 5.5 가 생각 끄기를 between_tools 로만 받고, Haiku 5.5 는 disabled 를 받되 xhigh · max effort 와 대화 도중의 effort 변경에서 400 이라고 적는다. 앱이 쓰는 조합이 모두 200 인지 본다. 서버 쪽 기록은 SDK 의 `fetch` 옵션으로 하고 브라우저 HAR 로는 안 잡힌다. 서버 측 대체 모델 재시도처럼 일부러 일으키기 어려운 것은 일어났을 때 원문 일부와 요청 번호를 남기는 장치만 둔다 | 호출 수십 건. Haiku 1토큰 위주라 1달러 안쪽 | '쉬는 중' 오분류와 스키마 불일치를 운영 전에 잡고, 받은 응답이 그대로 시험용 고정 표본이 된다 |

### 코드에서 spec 을 되짚어 어긋난 곳 찾기

정본에는 식별자가 많다. 설정 키(9절), 테이블(4절), 화면(3절), AI 호출(5절), 오류 행(7절 · 8절)이다. 이미 있는 장치는 둘이다. 코드 검토자(`code-reviewer`)는 작업 하나의 diff 를 정본과 맞대고, 분석가(`analyst`)는 정본과 코드 · 데이터를 읽기 전용으로 대조한다. 비어 있는 것은 차수 경계에서 코드 전체를 거꾸로 훑는 점검이다. 검토를 하나씩 통과한 변경이 쌓여 벌어지는 어긋남이 있을 수 있다(추정).

| 제안 | 하는 일 | 비용 | 효과 |
|---|---|---|---|
| 6. 식별자 대조 스크립트 | 코드에서 설정 키 · 테이블과 열 · Zod 스키마 이름 · 라우트를 기계로 뽑아(문서 다시 만들기) 정본의 표와 맞대고, 빠진 것 · 남은 것 · 이름이 다른 것을 목록으로 낸다. 설정값 원칙 점검도 같이 한다. 80 · 0.8 · 150 같은 설계 숫자가 코드에 박혀 있는지 찾는다 | 스크립트 반나절에서 하루. 이후 CI 한 단계 | '정본을 먼저 고치고 코드를 바꾼다'는 규칙을 기계가 매번 본다 |
| 7. 서술 대조 | 분석가 에이전트에게 코드에서 규칙(단원 통과 · 승급 · 복습 간격 · 오류 분기)을 읽어 규칙 목록으로 쓰게 하고 정본 절과 맞대게 한다. 규칙마다 코드 위치와 확신도를 달고 근거 없는 줄은 빈칸으로 남긴다. 복원문은 정본을 덮어쓰지 않고 어긋남 목록만 낸다. 이유는 코드에 없으므로 13절이 정본이다 | 차수마다 에이전트 한두 번(Opus xhigh)과 요청자 판정 시간 | 검토를 통과한 변경이 쌓여 정본과 벌어지는 것을 차수 경계에서 잡는다 |
| 8. 동작 기록 테스트 | DB 없는 순수 함수(단원 통과 · 승급 판정, 간격 반복 스케줄, 시드 검증기, 따라 말하기 일치율)에 대표 입력 표본을 넣고 지금 출력을 파일로 고정한다. 규칙이나 설정값을 바꾸는 날 바뀐 출력이 표로 드러난다. 새로 짜는 함수는 정의에서 시작하는 테스트가 먼저이고 이것은 그 뒤의 안전망이다 | 함수당 1~2시간 | "횟수로 승급하지 않는다" 같은 규칙이 조용히 훼손되는 일을 막는다 |

### 시드를 아이 눈으로 분해하기

정본 6.4 검증기는 지문 단어의 어휘 범위 밖 비율(seed.max_offband_ratio, 5% 이하), 학습 요소 범위, 글로서리, 금지 내용을 이미 검사한다. 풀이 검사는 정답 없이 Sonnet 5.5 가 문항을 풀게 해 앱 정답과 맞대니, 문항에서 정답을 거꾸로 짚는 일은 하고 있다. 시드 보기 화면에는 요청자가 칸마다 '알맞음 · 쉬움 · 어려움 · 오류'를 표시하는 장치도 있다. 비어 있는 것은 둘이다. 그 판정에 쓸 질문, 그리고 우리 어휘 배정표 자체를 바깥 기준에 대 보는 일이다.

| 제안 | 하는 일 | 비용 | 효과 |
|---|---|---|---|
| 9. 아이 눈 순회 체크 목록 | NN/g 의 인지 순회 검토(cognitive walkthrough, 처음 쓰는 사람의 눈으로 과제를 한 걸음씩 따라가며 걸음마다 묻는 검토)를 아이판으로 바꿔 시드 보기 화면 검토에 붙인다. 걸음마다 던지는 네 질문은 올바른 결과를 얻으려 시도할까, 올바른 행동이 있음을 알아챌까, 그 행동과 결과를 연결할까, 한 뒤에 진전이 보일까다. 우리 질문을 더한다. 화면에 행동이 하나인가, 안내를 읽지 않고도 할 일이 보이는가, 단계 어휘 범위 밖에 남은 모르는 말이 있는가, 틀렸을 때 해설이 4학년 눈에 이해되는가 | 표본 단원당 30분 안팎. 이미 하는 요청자 표본 검토에 칸을 늘리는 정도 | '쉬움 · 어려움' 판정의 기준이 사람과 날에 따라 흔들리지 않는다. 실제 아이 관찰은 사용 시험 때 따로 한다 |
| 10. 어휘 배정표의 바깥 기준 대조 | 완성된 어휘 배정표(영역 × 단계 × 단어)를 CEFR-J 단어 목록과 맞댄다. 낮은 단계에 높은 수준 단어가 몰렸거나 높은 단계가 쉬운 말만 쓰는 곳을 찾는다. 설계 결과에서 거꾸로 수준을 짚는 일이라 학습 설계자가 단 교육과정 근거를 독립적으로 확인하게 된다 | 스크립트 반나절. 목록은 연구 · 교육 · 상업 이용이 무료이고 출처를 밝히면 된다 | 어휘 범위가 CEFR 수준과 어긋난 단계를 본 생성 전에 찾는다 |

CEFR-J 목록은 A1에서 B2까지 7,801 항목이다. 정본의 Pre-A1 단계는 이 목록으로 덮지 못한다. 중국 · 대만 · 한국 교과서 말뭉치에서 뽑은 공통 어휘가 바탕이라고 페이지가 밝히지만, 초등 4학년 일상 어휘를 다 담았는지는 확인하지 못했다.

### 더 알아볼 것

- 경쟁 서비스 약관 원문이다. 윤선생 · 호두 · 리틀팍스 약관의 캡처 · 녹화 · 역분석 · 자동 수집 금지 문구를 읽지 못했다. 검색에서 리틀팍스 약관이 실린 가입 페이지 주소만 찾았다. 제안 1을 하기 전에 읽는다.
- 약관이 법의 예외를 없앨 수 있는지에 관한 한국 규정을 찾지 못했다.
- 저작권법 제104조의2 단서 여덟 호 가운데 여섯은 요약만 봤다.
- 부정경쟁방지법 (파)목의 요건과 해당 크롤링 사건의 민사 결과는 해설만 읽었다.
- 논문은 초록만 읽었다. 우리처럼 작은 저장소에서 같은 수치가 나온다는 보장은 없다.
- 구조화 출력 문서의 마지막 3천 자와 지출 한도 도달 오류를 설명하는 별도 페이지는 못 읽었다. 제안 5의 첫 관찰이 대신한다.
- 웹 보관소와 KIPRIS 는 열어 보지 않았다.
- 클린룸 방식을 다룬 한국 판결을 찾지 못했다.


절차는 여덟 걸음이다.

1. 묻는 것 정하기. 알고 싶은 것을 한 문장으로 쓰고 갈래(제품 분해 · 외부 API 관찰 · 코드에서 spec 되짚기 · 시드 분해) 하나를 고른다. 볼트 `index.md` 와 `docs/research/` 에 답이 이미 있으면 거기서 끝낸다.
2. 법 · 윤리 확인. 대상이 남의 서비스면 약관을 읽어 한 줄 적고 보호 조치와 개인정보를 확인한다. 디컴파일 · 앱 분해, 보호 조치 우회(로그인 · 유료 벽 · 인증서 고정), 남의 서버에 자동 요청, 아이 · 타인 계정 사용, 남의 문장 · 그림 · 음원 복사 가운데 하나라도 걸리면 멈추고 요청자에게 알린다. 법률 판단은 스킬이 내리지 않는다.
3. 가장 얕은 깊이부터. 깊이 표의 순서(공개 자료 → 직접 써 보기 → 소량 캡처 → 내 키 · 내 기기 관찰 → 코드 읽기 전용 분석)로 가고 답이 나오면 멈춘다.
4. 관찰 계획 쓰기. 질문 목록, 기대값(문서나 spec 이 말하는 것), 방법, 비밀값과 개인정보가 새는 길(HAR · 프록시 기록 · SDK debug 로그 · 캡처)과 막는 법을 적는다. 시험 계정 · 시험 키 · 어른이 읽는 시험 문장만 쓴다.
5. 관찰하고 원자료 남기기. 날짜와 환경(기기 · 브라우저 · 모델 · 판)을 달고 비밀값을 가린 기록을 남긴다. 서브에이전트는 읽기 전용으로 시킨다. 웹 조사는 Sonnet high, 코드와 spec 대조는 분석가(Opus xhigh)로 한다.
6. 기대와 관찰 맞대기. 같음 · 다름 · 못 봄으로 나눈다. 다름은 문서 오류 · 우리 가정 오류 · 환경 차이 가운데 어느 것인지 가린다. 모든 주장에 확인 정도(원문 · 검색 요약 · 추정)를 단다.
7. 결과 옮기기. 정본이 바뀌어야 하면 13절 결정 기록에 한 줄을 먼저 더한다. 조사는 `docs/research/`, 시험용 표본은 비밀값을 지운 고정 표본으로 올린다. 복원한 서술은 정본을 덮어쓰지 않는다. 표현은 옮기지 않고 사실과 구조만 쓴다.
8. 기록과 남은 질문. 볼트 기록 표시(`--mark-ingest`)를 하고 못 푼 질문은 '더 알아볼 것'에 적는다.
