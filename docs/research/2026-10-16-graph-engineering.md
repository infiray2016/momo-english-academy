# 그래프 엔지니어링은 무엇을 가리키고 우리 프로젝트에 어떻게 쓰나 (2026-10-16 조사)

요청자가 2026-10-16 03:3x 에 "AI SDLC, 그래프 엔지니어링, 리버스 엔지니어링을 활용해 프로젝트를 개발할 것이다. 잘 모르면 심층 조사해서 옵시디언에 저장하고 프로젝트에서 활용 가능하도록 구성해야 한다"고 했고, 컨트롤러 지시로 조사 담당이 그래프 엔지니어링을 맡았다. 질문은 둘이다. 이 이름은 실제로 무엇을 가리키는가. 그리고 문서 · 결정 · 시드 · 코드가 서로 이어져 있는 우리 프로젝트는 그것으로 무엇을 얻는가. 영어와 한국어 자료를 함께 봤고 논문 · 공식 문서 · 저장소 안내문을 먼저 열었다. 우리 쪽 수치는 `specs/` 와 볼트에서 직접 셌다. 리버스 엔지니어링과 AI SDLC 는 다루지 않고 닿는 곳만 짚었다. 출처는 끝에 모았고, 원문을 연 것 · 검색 요약만 본 것 · 추정을 가렸다.

## 한 줄 결론

"그래프 엔지니어링"은 2026년 7월에 이름이 붙은 새 말이다. 가장 자주 쓰이는 뜻은 AI 에이전트가 하는 일의 흐름을 점(node) · 선(edge) · 상태로 짜는 일(갈래 4)이다. 지식 그래프(갈래 1), LLM 용 지식 그래프(갈래 2), 코드 그래프(갈래 3)는 그 이름이 생기기 전부터 있던 별개의 기술이고, 일부 글이 같은 이름으로 묶어 부를 뿐이다. 한국어 실무서(위키독스)는 이 말이 두 분야에서 서로 다른 뜻으로 쓰인다고 직접 적었다.

우리 프로젝트에 값진 것은 갈래 1~3의 발상을 가볍게 쓰는 것이다. 이미 있는 정본(spec 번호, 볼트 링크, 시드 파일, 코드의 가져오기)에서 점과 선을 기계로 뽑고, 규칙으로 검사한다. 그래프 DB · GraphRAG · 코드 그래프 서버는 지금 규모에 과하다. 점은 요구사항 · 수용 기준 · 결정 · 설정 키 · 테이블 이름을 합쳐 약 340개이고, 볼트 모모 폴더는 파일 83개다.

제안은 열 가지이고 모두 스크립트나 설정 수준이다. 갈래 4는 앱에 필요 없고, 개발 과정은 이미 그 모양이다. 요청자가 말한 "그래프 엔지니어링"이 갈래 4였는지는 한 줄 확인이 필요하다(아래 "도입 순서와 요청자 확인").

"Anthropic 이 낸 그래프 엔지니어링 플레이북"이라는 PDF 와 글이 돌고 있다. 확인한 바로는 사실이 아니다. 그 PDF 는 11쪽이고 표지에 "독립 편집본이며 Anthropic 이나 Karpathy 와 관계없다"고 적혀 있다(AI Builder Club, 2026-07-30). 같은 글은 그 날짜까지 Anthropic 공개 자료에 그 이름의 문서 · 분야 · 제품이 없다고 적었고, 이 조사의 검색에서도 공식 문서는 나오지 않았다. 소문의 내용을 옮긴 BestHub 글(2026-07-28)의 단계는 추출 → 같은 대상 묶기 → 조립 → 요약 → 질의이고, 이는 2026-03-23 Anthropic 쿡북 「Knowledge graph construction with Claude」와 같다. 실체는 지식 그래프 만들기 안내서 하나다. 볼트에 정리된 "AI-Native SDLC 플레이북"은 별개의 문서다.

## 갈래 1 지식 그래프 엔지니어링

| 항목 | 내용 | 확인 |
|---|---|---|
| 핵심 개념 | 개체(entity)를 점으로, 관계를 선으로 둔다. 자료 모양이 둘이다. RDF 는 "주어-서술-목적어" 세 쌍(triple)이고, 속성 그래프(property graph)는 점과 선에 이름표와 속성을 붙인다. 여기에 틀(schema), 같은 대상 판별(identity), 맥락(context)이 따라온다 | 원문 |
| 틀 설계 | Noy 와 McGuinness 의 7단계. 범위와 쓰임 정하기 → 있는 것 재사용 → 용어 나열 → 분류와 계층 → 속성 → 속성 제약 → 실제 사례 채우기. 규칙 셋은 "정답 하나가 없고 쓰임에 달렸다 · 반복해서 다듬는다 · 도메인의 명사와 동사에 가깝게 한다"이다. 1단계에서 "이 틀이 답해야 할 질문"부터 적는다 | 원문 |
| 관계 종류 | 선마다 이름 · 방향 · 개수 제한 · 허용 근거를 적는다(Wavect 의 "최소 틀"). 출처 기록의 표준 어휘는 W3C PROV-O 의 Entity · Activity · Agent 와 wasGeneratedBy · used · wasDerivedFrom 이다 | 원문 |
| 질의 | RDF 는 SPARQL(세 쌍과 추론, 끝난다는 보장이 없다고 Neo4j 글이 지적). 속성 그래프는 Cypher · GQL(패턴 맞추기). GQL 은 속성 그래프의 ISO 질의어다. 관계형 DB 는 WITH RECURSIVE 로 따라가고 CYCLE 절로 순환을 잡는다 | 원문(Neo4j 글은 회사 글) |
| 갱신 | 판을 붙이고 바뀐 선만 고친다. 선에 출처 · 시각 · 확인 상태를 단다. Graphiti 는 옛 사실을 지우지 않고 무효로 표시한다 | 원문 |
| 품질 검사 | W3C SHACL(2017-07-20 권고)은 검사 규칙(shape)을 RDF 로 적고 데이터 그래프를 견준다. 대상 고르기(targetClass)와 개수 · 자료형 같은 제약 부품이 있다. Hogan 서베이는 품질 평가와 정제를 한 장으로 다룬다 | 원문 |
| 대표 도구 | Neo4j(속성 그래프), RDF 저장소, SHACL 검사기. 작은 규모는 NetworkX 나 Postgres 표 세 개(entities · relations · aliases)로 한다 | 원문(쿡북) |
| 도움이 될 때 | 여러 출처의 같은 대상을 합쳐 여러 걸음 건너 묻는 질문이 많을 때. 공유 어휘로 다른 팀의 자료를 맞출 때 | 원문 |
| 과할 때 | 한 번 쓰고 마는 질문, 한 문서 안의 답, 표로 안정된 자료(SQL 로 충분). RDF 쪽은 "틀이 완성돼야 배포할 수 있다"는 부담이 있다는 주장이 있다 | 원문(Wavect, Neo4j 글) |

| Zep · Graphiti(2025-01) | 시간 지식 그래프. 사실에 유효 기간이 있고, 모든 개체와 관계가 원자료(에피소드)로 되짚어 간다. 개체 · 관계 종류는 Pydantic 으로 정의한다. 저자 보고는 DMR 94.8% 대 MemGPT 93.4%, LongMemEval 최대 18.5% 향상이며 조건은 알 수 없다 | 원문, 수치는 저자 보고 |
| Anthropic 쿡북(2026-03-23) | 추출은 Haiku, 해소 · 요약 · 질의는 Sonnet, 조립은 모델 없이 NetworkX 로 한다. 2걸음 이웃을 세 쌍으로 풀어 모델에 주고 선을 인용하게 한다. 손으로 만든 정답 세트로 정밀도 · 재현율을 잰다. 예시 두 건은 정밀도 1.00 이나 재현율 0.55 와 0.38 이다. 해소 단계가 이름을 떨구거나 과하게 합칠 수 있다고 스스로 적었다 | 원문 |

| LLM Wiki(Karpathy, 2026-04-04) | 그래프 DB 없이 마크다운 위키 자체를 그래프로 쓴다. 원자료(불변) · 위키(LLM 이 유지) · 규칙 파일(CLAUDE.md 등) 세 층이다. 동작은 넣기 · 묻기 · 점검이다. index.md 는 쪽 목록, log.md 는 시간순 기록이다. 옵시디언 그래프 뷰로 중심 쪽과 들어오는 링크 없는 쪽을 본다. 큰 위키는 검색 도구(qmd)를 권한다. 효과를 보인 측정은 없다 | 원문 |
| 설계 순서(Wavect) | 비싸고 검증 가능한 질문 20~40개 → 최소 틀 → 같은 대상 판별(사람 검토) → 중요한 선마다 출처(출처 ID와 판 · 뽑은 시각과 방법 · 확신도 · 열람 범위 · 검토 상태) → 그래프와 글 검색 섞기 → 정답 세트로 정밀도 · 재현율 · 신선도 · 지연 · 성공당 비용 | 원문 |
| 도움이 될 때 | 여러 세션에 걸쳐 같은 사실을 쓰는 기억, 흩어진 문서에 대한 전체 질문 | 원문 |
| 과할 때 | 한 번 하는 조사, 한 문서 안의 답, 독립 작업, 정해진 순서, 안정된 표, 최신으로 유지할 수 없는 사실. 색인에 LLM 호출이 든다(공식 문서의 색인 단계가 LLM 추출과 요약이므로 비용이 든다고 본다) | 원문(Wavect), 비용은 추정 |

## 갈래 4 에이전트 작업 흐름 그래프

| 항목 | 내용 | 확인 |

| 정의 | 서베이 논문(2026-08-21, 저자 30여 명)은 "작업 수행 · 에이전트 조율 · 실행 상태 변화를 조직하고 통제하는 데 그래프 구조를 쓴다"고 정의한다. 앞선 엔지니어링이 에이전트 하나를 좋게 한다면 이것은 여러 에이전트로 된 시스템 수준이라고 자리매긴다. 분류는 작업 조직 · 에이전트 조율 · 실행 상태 관리 · 시스템 진화다. 소프트웨어 개발 사례로 MetaGPT · SWE-agent · OpenHands · Claude Code(하위 에이전트 · 점검 지점 · 훅)를 든다 | 원문(초록 · 서론 · 일부 절). 부록 11.2절은 열지 못함 |

| 패턴 | Anthropic 의 다섯 흐름은 연쇄 · 갈라 보내기 · 병렬 · 지휘자와 일꾼 · 생성자와 평가자 루프다(2024-12-19). 위키독스 책(이창근)은 조건 분기 · 병렬 · 지휘자와 일꾼 · 생성자와 평가자 루프 · 사람 승인 다섯 패턴을 LangGraph 로 만든다 | 원문 |

| 품질 검사 | 점마다 입출력 계약, 결정적 검증 관문, 오류 분류, 중복 실행에 안전한 부작용, 관측(추적 도구) | 원문 |

## 우리 프로젝트에 비추면

### 지금 있는 것

- 볼트는 이미 Karpathy 의 LLM Wiki 꼴이다. 원자료 · 위키 · 규칙 파일이 있고 index · log 와 기록 훅이 있다. 점검기(`vault_check.py --lint`)가 끊긴 링크 · 이름 겹침 · 들어오는 링크 없는 쪽 · sources 없는 위키 · 인용되지 않은 원자료 · 낡은 기준 판(basis)을 찾고, 머리말 sources 로 문서-관계 교차표를 다시 만든다. 갈래 2의 가벼운 형태를 이미 쓰는 셈이고, 선 종류는 링크와 근거(sources) 둘뿐이다.
- 볼트가 답해야 할 질문 다섯 가운데 셋은 이미 답한다. 위키 쪽이 어느 원자료에서 나왔나, 그 원자료를 쓰는 위키 쪽은 어디인가, 기준 판이 최신 spec 사본과 같은가다. 못 답하는 둘은 "spec 의 이 절이 바뀌면 고칠 위키 쪽은 어디인가"와 "이 결정(R · S · T · C)을 근거로 삼은 쪽은 어디이고 지금도 유효한가"다.
- spec 은 번호가 붙은 점이 약 340개다. 요구사항 FR 19 · NFR 9, 수용 기준 AC 100여 개, 결정 76개(R 15 · S 10 · T 8 · C 43), 설정 키 111개, 테이블 29개다. 선은 문장 속 번호 언급뿐이라 기계가 따라가지 못한다. 5회차 검토 보고의 지적은 관련 절 · 줄 · 결정 번호 · AC 번호를 여러 곳 나열한다. 예컨대 A5-23 은 4절 · 13절 C12 · AC-12h 세 곳이다. 검토자가 번호를 손으로 따라가며 일관성을 본 것이다. 어디를 같이 봐야 하는지 찾는 일은 기계가 할 수 있고, 맞는지 판단하는 일은 사람과 검토 에이전트가 한다.
- 시드 검증기(6.4)는 칸 하나를 규격에 견주는 검사가 중심이다. 그림 키가 카탈로그에 있는가, 평가 문항에 연결 단원이 있는가 같은 참조 검사는 일부 있다. 칸 사이 관계의 전체 지도는 표에 없다. 단원 240개에 단원마다 목표 어휘 30개이므로 어휘 칸이 약 7,200개다.
- 코드는 아직 없다. 구조 규칙은 CLAUDE.md 문장으로만 있다. 순수 함수는 DB 에 의존하지 않는다, AI 호출은 서버에서만 한다, 설계 숫자는 설정값이다.
- 앱의 AI 호출은 한 번에 끝나는 구조화 출력이라 갈래 4의 흐름 그래프가 필요 없다. 개발 과정(intent → spec → plan → build, 구현자와 검토자 분리, 회차 루프)은 이미 생성자와 평가자 루프 모양이고 볼트에 그림이 있다.

| P10 | 코드 | dependency-cruiser 의 mermaid 출력으로 모듈 지도를 `docs/` 에 만들고 CLAUDE.md 에서 한 줄로 가리킨다. 코드 그래프 도구(Graphify · codemap · SCIP)는 지금 들이지 않고 도입 기준만 적어 둔다. 기준은 소스 파일이 수백 개를 넘고 에이전트가 탐색에 턴을 많이 쓸 때이며, 같은 질문 열 개를 grep 과 그래프로 견주는 작은 시험을 먼저 한다. 기준 숫자는 도입을 논의할 때 요청자가 정한다 | 지도 30분. 비교 시험은 그때 가서 반나절 이상 | 지금 효과는 작다. 에이전트가 첫 턴에 지도를 읽는다 | 1-가 뼈대 |

### 지금 하지 않을 것

| 하지 않을 것 | 이유 |
|---|---|
| 그래프 DB(Neo4j 등) | 점 약 340개와 파일 83개는 JSON 과 메모리에서 끝난다. 쿡북도 NetworkX 는 수십만 선까지 괜찮다고 한다. 우리 DB 가 이미 Postgres 라 필요해지면 재귀 질의로 된다 |

| 컨텍스트 그래프 제품 | 13절 결정 기록과 검토 장부가 "누가 왜 정했나"를 사람 손으로 이미 남긴다 |
| 코드 그래프 서버 | 코드가 없다. 근거가 저자 자체 측정뿐이고 표본이 작다(질문 6개, 50개) |

| 결정 한 건마다 볼트 쪽 만들기 | 정본은 13절 표다. 쪼개면 이중 관리가 된다. 볼트에는 결정 번호를 근거로 삼은 쪽의 색인만 둔다(P1) |

### 도입 순서와 요청자 확인

- 순서는 P3 를 먼저 한다(문서 단계에서 바로 쓴다). 다음이 P8 · P10(1-가 뼈대), P6 · P7(시드 검증기를 만들 때), P1 · P2(볼트 정비 때 한 번에), P4 · P5(코드와 테스트가 생긴 뒤), 마지막이 P9(선택)다.
- 원칙은 하나다. 그래프는 정본에서 뽑은 파생물이다. 틀리면 정본(spec · 시드 · 코드)을 고치고 그래프를 다시 뽑는다. 그래프 파일을 손으로 고치지 않는다.
- 요청자가 말한 "그래프 엔지니어링"이 갈래 4(에이전트 흐름을 그래프로 짜는 일)였다면, 이 문서는 앱에 필요 없다고 결론 냈다. 개발 과정에 쓰려는 것이라면 이미 있는 AI-SDLC 그림과 장부가 그 역할을 한다. 갈래 1~3 쪽이었다면 위 제안이 답이다. 어느 쪽인지 한 줄 확인이 필요하다.
- 리버스 엔지니어링과 닿는 곳은 둘이다. 외부 프로그램을 뜯어본 결과는 이미 표로 정리돼 있어(`2026-10-15-program-reverse-engineering.md`) 그래프로 바꿀 이득이 작다. 코드 리버스 엔지니어링(CodeConcise 꼴)은 뜯어볼 기존 코드가 없어 해당이 없다.

```markdown
# 그래프 엔지니어링 (정본에서 점과 선을 뽑아 검사하기)

## 켜지는 때와 켜지지 않는 때
- 켜진다. 같은 번호나 이름이 여러 문서에 흩어져 "어디를 같이 고쳐야 하나"가 질문일 때. 검토 회차가 번호 대조에 시간을 쓸 때. 시드나 코드에 "칸 사이 규칙"을 넣을 때.
- 켜지지 않는다. 한 문서 안의 답, 한 번 하는 질문, 표로 충분한 자료, 에이전트 하나로 되는 일.

## 절차
1. 질문부터 쓴다. 이 그래프가 답할 질문 3~10개를 문장으로 적는다. 질문이 없으면 여기서 멈춘다.
2. 갈래를 고른다. 볼트(링크 · 머리말), 추적(spec 번호), 시드(JSON 참조), 코드(가져오기) 가운데 하나다. 추출형 지식 그래프와 에이전트 흐름은 "하지 않을 것" 표를 먼저 본다.
3. 점과 선의 종류를 표로 정한다. 점 종류는 7개 이하로 하고 선은 이름 · 방향 · 개수 제한을 적는다. 이미 있는 번호 체계와 머리말 속성을 그대로 쓴다.
4. 정본에서 결정적으로 뽑는다. 정규식 · 파서 · 구문 트리를 쓴다. LLM 으로 뽑는 것은 마지막 수단이다. 쓰면 모든 선에 출처 · 확신도 · 확인 상태를 달고 사람이 표본을 본다.
5. 검사 규칙을 쓴다. 규칙마다 한 줄 문장과 실패 예를 함께 적는다(끊긴 선 · 들어오는 선 없는 점 · 순환 · 개수 위반 · 낡은 기준). 순수 함수와 테스트를 먼저 쓴다.
6. 돌리고 위반을 낸다. 파일 · 줄 · 규칙 이름으로 낸다. 고치는 곳은 정본이다. 그래프 파일은 파생물이라 손대지 않는다.
7. 붙인다. `vault_check.py --lint`, CI, 커밋 전 훅 가운데 맞는 곳에 건다. 규칙이 설계를 바꾸면 13절 결정 기록에 한 줄을 먼저 더한다.
8. 되돌아본다. 질문이 답해졌는지, 검사가 실제 오류를 몇 건 잡았는지, 거짓 경보가 몇 건인지 적는다. 두 번 연속 잡은 것이 없으면 걷어낸다.

## 단계에 끼는 자리
| 단계 | 하는 일 |
|---|---|
| intent | 그래프가 답할 질문을 제약에 적는다 |
| spec | 점 · 선 종류와 규칙을 적고 결정 기록에 한 줄 더한다 |
| plan | 검사 작업을 작업 순서와 증명(테스트)에 넣는다 |
| build | 순수 함수 · Vitest · CI 로 구현한다 |
| 검토 | 위반 목록을 검토자 입력으로 준다 |

## 지킬 것
- 용어는 점(node) · 선(edge) · 상태로 쓴다. 문서와 화면에 "트랙" · "유닛"을 쓰지 않는다.
- 설계 숫자는 설정값이다. 비밀값 · 아이 이름은 기록하지 않는다.
```
